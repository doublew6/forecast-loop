# forecast-loop

**Language / 语言: English · [简体中文](README.md)**

> Forecast. Explain. Resolve. Learn.

forecast-loop is a **verifiable forecasting agent framework**. Forecast signals
may be entered directly by people or generated by deterministic quantitative
programs or AI models. Regardless of source, every signal follows the same
rules for ex-ante sealing, evidence freezing, outcome evaluation, and audit.

The project is inspired by Ray Dalio's public description of
[Idea Meritocracy / Believability-Weighted Decision Making][principles]:
credibility should come from a repeated track record in the relevant domain
and from causal explanations that can be tested and falsified. forecast-loop
borrows this governance idea but is not affiliated with or endorsed by
Bridgewater.

A **Forecast** is sealed before its outcome is revealed. The **Loop** connects
forecasts, reasons, outcomes, reflections, Lessons, and future forecasts. The
project focuses on reproducible track records rather than the number of agents,
the confidence of their language, or a single profitable prediction.

## Core loop

```text
Declare signal source, identity, and version
  -> form an independent direction, probability, and rationale
  -> state the strongest counterargument and invalidation conditions
  -> freeze inputs, citations, and outputs before the outcome
  -> evaluate direction and probability at maturity
  -> classify right reason / lucky correct / wrong / unresolved
  -> create future Lessons through replay, review, and versioned gates
```

Regardless of who produces a signal, the system maintains five boundaries:

- Model output is an untrusted draft. Deterministic Python owns time checks,
  schemas, hashes, citations, aggregation, persistence, and scoring.
- A forecast may use only evidence and Wiki versions published before its
  cutoff. Historical snapshots and forecasts are immutable.
- Track records never change formal weights automatically. Policy changes
  require sufficient samples, replay, and explicit human approval.
- External data connects only through read-only adapters, snapshots, or
  replicas and is never written back to its owner.
- The system never connects to a broker, places orders, or writes to upstream
  production databases.

## Input methods

Every source shares the same identity, versioning, sealing, and evaluation
discipline:

| Source | Input | Constraint |
| --- | --- | --- |
| Human | Direction, rationale, strongest counterargument, and invalidation conditions | The system forecast stays hidden before submission; sealed records are immutable |
| AI model | Structured draft with direction, probabilities, rationale, and citations | May produce drafts only; deterministic validation is mandatory |
| Quantitative program | Signal bundle with code, parameter, data, and model hashes | Read-only input, used for shadow evaluation by default |
| Deterministic rules | Validation, aggregation, persistence, and scoring results | Rules must be versioned and replayable |

Human input uses the same prediction targets and trusted market outcomes as
other sources, so it can build an independent scorecard. Different sources may
bind different evidence, however, and the system does not assume identical
information sets or scoring capabilities.

## Research configuration

- Default targets: CSI 300, CSI 500, CSI 1000, ChiNext Index, and STAR 50.
- Optional markets: versioned Market Universe files may define Hong Kong or US
  markets, indexes, or individual equities.
- Horizons: cumulative return over the next two trading days as the primary
  forecast, with the next trading day as a secondary forecast.
- Ex-ante direction: must be either up or down; outcomes are evaluated as up,
  small move, or down.
- Product: a local single-user research console, not investment advice or an
  automated trading system.

Each run freezes its target Universe, market clock, evidence cutoff, and
research versions. Credibility evidence is partitioned by source, version,
model, target, and horizon. A new aggregation policy affects only runs after
its activation and never rewrites historical forecasts. See
[Markets and targets](docs/market-universes.md) and
[credibility governance](docs/believability.md).

## Architecture

```text
read-only sources + versioned Wiki
               |
               v
      frozen evidence snapshot
               |
               v
 human / model / quant signals
               |
               v
 deterministic validation + aggregation
               |
               v
      immutable forecasts
               |
               v
 evaluation -> reflection -> gated lessons
```

The backend uses FastAPI, LangChain, and LangGraph. The frontend uses React,
TypeScript, and Vite. Local state, forecasts, and evaluations are stored in
SQLite. Core results do not depend on LangSmith.

### Standalone Wiki Atlas frontend

`wiki-frontend/` is a temporary standalone knowledge workbench organized around
domains, immutable raw materials, versioned Wiki pages, provenance, and review
feedback. It is D1-only and includes manual uploads, scheduled collection jobs,
a same-origin API proxy, and an authenticated public gateway with failed-login
limits. See the [Wiki Atlas README](wiki-frontend/README.md) for setup and
security details.

Public extension points follow a Ports/Adapters design: external sources return
time-bound, content-hashed frozen snapshots; inference may produce only
restricted drafts; deterministic code validates and persists them. Licensed
fields, credentials, private paths, and provider mappings remain outside the
repository. forecast-loop accepts only source-neutral, read-only sealed
artifacts.

## Quick start

You need Python 3.11+, [uv](https://docs.astral.sh/uv/) 0.9.8, and Node.js
20.19+. Docker uses Python 3.12.13, while CI uses the `uv`-managed Python
3.12.12; both use Node.js 22 to reduce environment drift.

```bash
cp .env.example .env
make install
make migrate
make backend
```

Start the durable worker and frontend in two additional terminals:

```bash
make worker
make frontend
```

Open `http://localhost:5173`. The default
`VERICOUNCIL_EXECUTION_PROVIDER=demo` requires no model key. Demo mode uses a
deterministic offline generator to verify the workflow and UI; it is not
intelligent research and never enters formal scoring.

### Change markets or targets

Select a versioned Universe and set the matching market timezone:

```bash
export FORECAST_LOOP_MARKET_UNIVERSE_PATH=./examples/market-universes/us-index-and-equities.json
export VERICOUNCIL_TIMEZONE=America/New_York
```

After restart, the research console and human judgment page use the new
targets. Live mode also requires a read-only Evidence Snapshot for that market.
The configuration file does not download or authorize market data.

### Daily quantitative research

Quantitative programs submit sealed bundles through the generic read-only port.
Each bundle binds code, parameters, model, inputs, and Market Universe hashes
and must match the run's Evidence Snapshot. The public repository does not ship
a specific training framework, production-data adapter, or private research
parameters; those implementations belong in independent extensions.

Quant remains shadow-only by default and cannot write back to an external data
source or bypass human activation. See the
[Quant data protocol](docs/quant-adapter.md) for the public contract, synthetic
fixture, and compatibility tests.

### Docker

```bash
cp .env.example .env
make docker-config
make docker-up
```

The frontend is available at `http://127.0.0.1:4173`, and the API at
`http://127.0.0.1:8000/api`. Compose binds only to loopback by default. Do not
expose these ports without authentication, TLS, and network access controls.

The static GitHub Pages Demo is disabled by default. To enable it, select
GitHub Actions as the Pages source and set the `PAGES_ENABLED=true` repository
variable.

## Core workflows

### 1. Record your own judgment first

After migration, open `http://localhost:5173/judgments`. The page initially
hides the system forecast and asks the user to choose up or down, then record a
rationale, strongest counterargument, and observable invalidation condition.
The comparison appears only after the judgment is sealed.

The CLI is also available. Pass reasons through files to keep them out of shell
history:

```bash
uv run forecast-loop judgment record \
  --forecast-id <id> \
  --direction up \
  --confidence 0.67 \
  --rationale-file ./input/rationale.md \
  --counter-evidence-file ./input/counter.md \
  --invalidation-file ./input/invalidation.md \
  --blind

uv run forecast-loop judgment verify <judgment-id>
uv run forecast-loop judgment export <judgment-id>
```

Only Live judgments submitted before the cutoff with a declaration that the
system forecast has not been viewed enter the independent shadow score.

### 2. Daily Reflection

Reflection processes only completed Live D1/D2 forecasts. Demo runs never
produce formal Reflections, Lessons, or Wiki inputs.

```bash
make migrate
make market-snapshot
make market-import
make reflection-prepare
```

Source-discovery drafts are written to `source-discovery/drafts.json`.
Deterministic code freezes a trusted capture bundle, analysis drafts are
written to `analysis/drafts.json`, and deterministic commands publish and
render the result:

```bash
make reflection-freeze-sources ARGS="./data/reflections/<job-id> --sources ./input/captures.json"
make reflection-finalize ARGS="./data/reflections/<job-id>"
make reflection-render ARGS="<reflection-id>"
```

The project has no built-in generic web crawler. Without a trusted capture
bundle, unverified causes must remain `unresolved`. Lessons remain in shadow
until sample and human-review gates are satisfied.

### 3. Snapshots and portable audits

Build an immutable evidence snapshot from a reviewed draft:

```bash
make snapshot DRAFT=path/to/draft.json OUTPUT=data/snapshots/2026-07-13.json

uv run forecast-loop snapshot validate \
  data/snapshots/2026-07-13.json \
  --root data/snapshots \
  --as-of 2026-07-13T16:00:00+08:00
```

SHA-256 can detect changes after packaging, but it cannot prove that a source
is authentic, a fact is correct, or the evidence is complete. Formal forecasts
still require source, event-time, and visibility-time review. Revisions must
create a new snapshot and run.

Completed runs can be exported and verified offline:

```bash
uv run forecast-loop run export <run-id>
uv run forecast-loop run verify data/exports/<run-id>

uv run forecast-loop audit export <job-dir> \
  --handoff-root data/handoffs \
  --run-bundle data/exports/<run-id>
uv run forecast-loop audit verify data/audit-bundles/<run-id>
```

## Important boundary

forecast-loop is a research, evidence, and audit tool, not investment advice.
It does not trade automatically, and Demo results never enter formal scoring.
When critical inputs are incomplete, the system must fail with an explicit
reason rather than silently reuse stale data.

The current version is **v0.1.0 early release**. Pre-1.0 public interfaces may
still evolve under the [compatibility policy](docs/compatibility-policy.md).
